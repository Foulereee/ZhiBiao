## 2. 现在的内容还会回滚吗？

**结论：重启不会；"用镜像重建容器"曾经会——但 2026-10-05 15:52 已完成固化，现在两者都不会了。**

| 操作 | 会不会退回旧代码 | 说明 |
|---|---|---|
| `docker restart` / 宿主机重启 / 容器崩溃自动拉起 | ❌ 不回滚 | 改动在容器可写层，重启保留（本次已实测 6 次以上） |
| 每日 03:30 全量备份 | ❌ 不回滚 | 只读打包到 `/opt/backups/`，不覆盖运行代码 |
| 前端看门狗（每 10 分钟） | 只会回滚**前端** dist，且仅在界面标记缺失时 | 不碰后端；本次没改前端，无影响 |
| `docker compose up -d`（不需要重建容器时） | ❌ 不回滚 | 沿用现有容器 |
| `docker compose up -d`（compose 判定需重建：改了 compose 文件、改了被引用的 `.env` 变量、镜像 tag 变化） | 固化**前**会回滚到 9/23 旧代码；**现已固化 → 不会** | 新容器从镜像层启动，镜像已是新代码 |
| `docker compose down` + `up -d` | 固化**前**一定回滚；**现已固化 → 不会** | 容器重建，但镜像已是新代码 |
| `docker compose up -d --build` | ❌ 不回滚，且**从此固化** | 镜像用 `/opt/bidmaster` 当前源码重建 |
| 换/加载别的镜像（`docker load` 旧 tar） | ✅ 回滚 | 镜像即代码 |

**消除风险（已于 2026-10-05 15:52 执行完毕）**

```bash
bash /opt/bidmaster/deploy/rebuild_and_verify.sh
```
它会：给当前镜像打快照 tag（`bidmaster-pro-api:rollback-<时间戳>`）→ 用宿主源码重建镜像 → 重建 3 个后端容器 →
验证（`/api/health`、旧站首页、**容器内代码 md5 是否等于宿主**、登录接口、OpenAPI 路由数、日志异常）→
**任何一项不过就自动把镜像换回快照并重建**。之后 `down/up` 也不会回滚了。

> 实测结果（2026-10-05 15:52）：构建复用缓存仅数秒；3 个容器重建后 78 秒 `/api/health` 回到 200；
> 22 个改动文件宿主与容器 md5 全部一致；旧站首页 200；容器内合成文档排版探针通过
> （封面 22/36pt 居中保留、页脚「第 X 页」保留、正文缩进 0.85cm、标题 16/15pt、目录制表位 15.6cm、书签违例 0）；
> 业务数据未变（users 1 / projects 2 / chapters 492）；回滚快照 `bidmaster-pro-api:rollback-20261005_155245` 已保留。

只打镜像、不中断业务（容器仍跑旧层，下次重建时生效）：
```bash
bash /opt/bidmaster/deploy/rebuild_and_verify.sh --no-recreate
```

## 3. 日常改代码 → 上线（标准流程）

```bash
# 1) 在本地（或直接在服务器）改 /opt/bidmaster 下的源码
# 2) 语法与静态自检（可选但推荐）
python3 -m py_compile services/routers/generate.py     # 逐个改动文件
bash /opt/bidmaster/deploy/rebuild_and_verify.sh       # 构建+重建+验证+失败自动回滚
# 3) 浏览器 Ctrl+F5；本轮重启会清空内存登录态，需重新登录
```

> 不要再用 `docker cp` + `restart` 的方式改代码：那样只有**运行中的容器**是新代码，
> 一旦容器被重建就会回滚（本次修复最初也是这样上的，现已用重建方式固化）。
> 若临时应急必须 `docker cp`，务必紧接着跑一次固化脚本。

## 4. 完整迁移到另一台服务器

### 4.1 在老服务器导出

```bash
cd /opt/bidmaster/deploy        # 或任意目录，用 bash 调用即可
bash export_all.sh              # 约 30 秒，产物约 26MB
# 如果新服务器不能访问外网（构建时需要拉 pypi），再加上镜像一起打（约 +0.5~1.4GB）：
bash export_all.sh --with-image
```

产物（默认在 `/opt/backups/`）：

| 文件 | 内容 |
|---|---|
| `migrate_<ts>.tar.gz` | **单文件迁移包**（下面这些都装在里面） |
| `migrate_<ts>/db_bidmaster.sql` | 数据库全量（`--clean --if-exists --no-owner`，可直接覆盖已建表的库） |
| `migrate_<ts>/db_roles.sql` | 角色/权限 |
| `migrate_<ts>/backend_src.tgz` | 后端源码（含本次全部修复） |
| `migrate_<ts>/frontend_dist_live.tgz` | 80 端口线上前端产物（bundle `index-Dxt6QZpi.js`） |
| `migrate_<ts>/frontend_src.tgz` | 前端源码（日后改界面用） |
| `migrate_<ts>/web_nginx.conf` | 站点 nginx 配置 |
| `migrate_<ts>/volume_*.tgz` | `projects / uploads / chroma / miniodata` 数据卷 |
| `migrate_<ts>/_opt_bidmaster_.env` | **环境变量与全部密钥**（权限已设 600） |
| `migrate_<ts>/restore_web_container.sh` | 新服务器上重建 80 端口站点的脚本 |
| `migrate_<ts>/expected_counts.txt` | 期望行数（导入后自动核对） |
| `migrate_<ts>/containers_inspect.json`、`containers.txt`、`images.txt` | 原环境容器/镜像的完整信息 |
| `migrate_<ts>/SHA256SUMS` | 校验和 |
| `api_image_<ts>.tar.gz` | 仅 `--with-image` 时生成 |

### 4.2 传包

```bash
scp /opt/backups/migrate_<ts>.tar.gz root@新服务器:/root/
# 包内含明文密钥，用加密通道；落地后 chmod 600
```

### 4.3 在新服务器导入

前置：Linux + Docker 24+ + `docker compose` v2；建议 ≥2 核 4GB 内存、≥20GB 空闲磁盘；对外放通 80（主入口）与 3000（备用）。

```bash
# 先干跑一遍看它要做什么（不改动系统）
bash import_all.sh --bundle migrate_<ts>.tar.gz --dry-run

# 正式导入
bash import_all.sh --bundle migrate_<ts>.tar.gz
# 若拷了镜像包（新服务器不能联网构建时用这个）
bash import_all.sh --bundle migrate_<ts>.tar.gz --image api_image_<ts>.tar.gz
```

脚本做的事（9 步）：
1. 前置检查（docker / compose / 目录占用 / 磁盘）
2. 解包 + SHA256 校验
3. 放置后端源码到 `/opt/bidmaster`，重建 `docker/.env -> ../.env` 软链
4. 放置前端到 `/opt/bidmaster-web/{dist,nginx.conf}`
5. 准备 api 镜像（`docker load` 或 `docker compose build api`）
6. 起 `postgres` + `redis`（`--profile infra`）
7. 恢复 4 个数据卷（用容器把 tar 解进卷里）
8. 恢复数据库（先 `DROP SCHEMA public CASCADE`，再灌 `db_bidmaster.sql`），并**逐表核对期望行数**
9. 起 `api / celery-worker / celery-beat`，再重建 80 端口站点容器

### 4.4 导入后必须人工确认

1. 浏览器打开 `http://<新服务器IP>/`，用原账号登录（用户随数据库迁移）
2. 打开一个项目 → **导出 Word（带排版）**：封面 22pt/36pt 居中、页脚「第 X 页」、正文首行缩进 2 字符、目录页码点线对齐右边界
3. 上传一份招标文件 → 解析 → 全量检查（验证 `uploads` 卷权限与 LLM 密钥）
4. 想换密钥/模型：编辑 `/opt/bidmaster/.env`，然后
   `cd /opt/bidmaster/docker && docker compose up -d --no-deps --force-recreate api celery-worker celery-beat`
5. 域名/HTTPS：在 80 端口站点前再加一层宿主 nginx 或云负载均衡；**不要改 `bidmaster-net` 网络名**（nginx 里写死了 `http://api:8000`）
6. 清理：确认无误后删除迁移包与包内 `.env`，或轮换一次密钥

## 5. 回滚方案（三条线各自独立）

| 线 | 回滚方式 | 数据影响 |
|---|---|---|
| **代码**（后端） | `docker tag bidmaster-pro-api:rollback-<ts> bidmaster-pro-api:latest && cd /opt/bidmaster/docker && docker compose up -d --no-deps api celery-worker celery-beat` | 无（不动数据库） |
| **代码**（回到 9/23 的镜像原版） | `docker images | grep bidmaster-pro-api` 找到旧 tag 后同上替换 latest | 无 |
| **源码**（宿主目录） | `/opt/backups/` 里的历史整包（`bidmaster_full_<日期>.tar.gz`）含 `backend_src.tgz`；或 `/opt/bidmaster/.backup_v12*`、`.backup_v13*` 等目录 | 无 |
| **前端** | 看门狗快照：`ls -t /opt/bidmaster-web-snap/web_dist_guard_*.tgz | head -1`，解到 `/opt/bidmaster-web/dist` 后 `docker restart bidmaster-web` | 无 |
| **数据库** | `docker exec -i docker-postgres-1 psql -U postgres -d bidmaster < 某个 db_bidmaster.sql`（先 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`） | 会回到备份时刻的数据 |
| **业务文件** | `docker run --rm -v docker_uploads:/d -v /path:/src postgres:16-alpine tar -xzf /src/volume_uploads.tgz -C /d` | 同上 |

> 数据库/文件回滚只在你明确要求时做：本次修复全程没有改动任何业务数据。

## 6. 备份现状

- 每天 **03:30** 自动全量备份到 `/opt/backups/<日期>/`，并打整包 `bidmaster_full_<日期>.tar.gz`（约 20MB）。
- 包内含：`db_bidmaster.sql`、`db_roles.sql`、`backend_src.tgz`、`frontend_dist_live.tgz`、`frontend_src.tgz`、
  `volume_{chroma,projects,uploads,miniodata}.tgz`、`.env`、compose 文件、nginx 配置、容器/镜像清单、`SHA256SUMS`。
- 也就是说：**日常已有可迁移的整包备份**，`export_all.sh` 只是在此基础上补齐"一键导入脚本 + 站点重建脚本 + 期望行数核对"。
- 建议：把 `/opt/backups/` 定期同步到异地（对象存储/NAS），并定期做一次"新机器试恢复"演练。

## 7. 注意事项与常见坑

1. **`UVICORN_WORKERS=1` 不要改**：任务状态与部分会话目前在进程内存（`TaskManager`），多 worker 会出现"任务查不到/状态不一致"。
2. **后端只监听回环**：`docker-api-1` 是 `127.0.0.1:8000`，外部只能通过 80 端口的 nginx 访问，这是有意的安全设计，别改成 `0.0.0.0`。
3. **80 端口站点容器不由 compose 管理**：改动它要用 `deploy/` 里的 `restore_web_container.sh`（已在迁移包内），不要 `docker compose down`。
4. **前端看门狗会自动回滚界面**：`*/10` 检查线上 bundle 是否含关键界面标记，缺失就用最近快照恢复 dist。改前端后要更新它的快照目录，否则可能被回滚。
5. **上传上限 50MB**（后端 `MAX_UPLOAD_BYTES`，分块读取超限即 413）；招标文件解析结果与上传文件长期保留在 `/app/uploads`、`/app/projects`（对应两个数据卷）。
6. **密钥**：LLM / 向量模型 / MinerU 的 key 都在 `/opt/bidmaster/.env`。迁移包会带上它们，注意传输与留存安全；换环境后建议轮换。
7. **磁盘**：当前 Docker 镜像占 5GB（其中 4.2GB 可回收）。空间紧张时：
   `docker image prune -a`（会删掉不用的旧镜像，注意别删掉 `bidmaster-pro-api:rollback-*` 快照）、`docker builder prune`。
8. **脚本换行符**：`deploy/*.sh` 是 LF（Linux 脚本），用 `bash xxx.sh` 调用；若你在 Windows 上编辑后变 CRLF，`./xxx.sh` 会报 `bad interpreter`，改用 `bash xxx.sh` 即可。
9. **迁移到新机器后首次启动**：API 会自动 `create_all` 建表（幂等），但**数据要靠 `db_bidmaster.sql` 恢复**；只搬源码不搬库＝空系统。
10. **不同服务器架构**：若新服务器是 ARM，`--with-image` 的镜像不能用，必须用 `docker compose build` 在本机构建。

## 8. 一句话总结

- **代码改动现在在"宿主源码 + 运行容器"里，重启不会回滚；但 `docker compose down/up` 会退回 9/23 的镜像。**
- 跑一次 `deploy/rebuild_and_verify.sh` 就把它烧进镜像，**从此任何重建都不回滚**（失败会自动回滚到构建前状态）。
- 搬到别的服务器：老机器 `export_all.sh` → 传 26MB 的包 → 新机器 `import_all.sh`，脚本会自动恢复数据库、数据卷、前端与 80 端口站点，并核对行数。
