# 全新主机完整部署手册（含全新数据库）

> 目标：在**另一台主机**上从零部署出一套**完全独立**的智标系统——自带新的 PostgreSQL 实例、新的数据卷、新的 Redis，
> 不连接、不依赖原来那台机器上的任何东西。
> 配套脚本：[export_all.sh](export_all.sh)（老机导出）、[import_all.sh](import_all.sh)（新机导入）、[seed_admin.py](seed_admin.py)（空库建管理员）、[rebuild_and_verify.sh](rebuild_and_verify.sh)（上线/固化）。
> 本文里标注「已实测」的结论，都是在当前生产机上真实跑出来的。

---

## 0. 先选你要哪种结果

| 目标 | 用哪种模式 | 新数据库里有什么 |
|---|---|---|
| **把现有系统整体搬到新主机**（用户、项目、章节、上传文件都跟过去） | 迁移模式：`import_all.sh --bundle ...` | 新 PostgreSQL 实例 + 恢复的历史数据（已实测：22 张表、行数与旧库逐表一致） |
| **在新主机上起一套全新的空系统**（不要历史数据） | 全新模式：`import_all.sh --bundle ... --fresh --admin-email ... --admin-password ...` | 新 PostgreSQL 实例 + 自动建表 + 新建管理员账号（已实测） |

两种模式都是**新的数据库实例**（新容器 `docker-postgres-1` + 新卷 `docker_pgdata`），与原机器完全隔开。

## 1. 新主机准备

| 项目 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Linux（x86_64） | 若用 ARM 机器，**不能**用 `--with-image` 的镜像，必须在本机 `docker compose build` |
| Docker | 24+，且 `docker compose version` 可用（compose v2） | `docker compose version` 不通就得装 compose 插件 |
| 资源 | 建议 ≥2 核 4GB 内存、≥20GB 空闲磁盘 | 当前老机器是 2 核 1.8GB，能跑但偏紧（构建镜像时更吃内存） |
| 端口 | 对外放通 **80**（主入口）与 **3000**（备用）；80 不能被宿主 nginx/apache 占用 | 后端 8000、数据库 5432、Redis 16379 **只绑 127.0.0.1**，不需要对外 |
| 时区 | `Asia/Shanghai` | 容器内已设 `TZ=Asia/Shanghai`；宿主也建议 `timedatectl set-timezone Asia/Shanghai` |
| 出网 | 若不用 `--with-image`，需要能访问 `mirrors.aliyun.com`（apt/pypi 镜像） | 否则请在有网机器上 `docker save` 镜像带过去 |
| 目录 | `/opt/bidmaster`（后端）、`/opt/bidmaster-web`（前端+运维脚本）、`/opt/backups`（备份）、`/opt/rollback_snapshots`（前端快照） | 导入脚本会自动创建 |

```bash
# 新主机上先装 Docker（以常见发行版为例）
curl -fsSL https://get.docker.com | sh
systemctl enable --now docker
docker compose version || apt-get install -y docker-compose-plugin
```

## 2. 在老主机上导出迁移包

```bash
# 建议挑业务空闲时段执行（导出过程中数据库是事务一致的，文件卷是快照）
bash /opt/bidmaster/deploy/export_all.sh
# 新主机不通外网时，把镜像也一起打进去：
bash /opt/bidmaster/deploy/export_all.sh --with-image

# 想让"库 + 文件"严格同一时刻，可先停写入方 30 秒：
#   cd /opt/bidmaster/docker && docker compose stop api celery-worker
#   bash /opt/bidmaster/deploy/export_all.sh
#   cd /opt/bidmaster/docker && docker compose start api celery-worker
```

产物：`/opt/backups/migrate_<时间戳>.tar.gz`（当前约 26MB，权限 600）。包内包含：

| 内容 | 用途 |
|---|---|
| `db_bidmaster.sql`（`--clean --if-exists --no-owner`） | 可直接灌进一个全新的库（已实测：0 报错、行数逐表一致） |
| `db_roles.sql` | 角色权限 |
| `backend_src.tgz` | 后端源码（含全部修复） |
| `frontend_dist_live.tgz` + `web_nginx.conf` | 80 端口线上前端产物与站点配置（新主机不用重新构建前端） |
| `frontend_src.tgz` | 前端源码（日后改界面） |
| `volume_{projects,uploads,chroma,miniodata}.tgz` | 业务文件、向量库 |
| `ops_scripts.tgz` + `crontab.txt` | 每日备份脚本、前端守门脚本、前端看门狗、原定时任务（**新主机要重装**） |
| `seed_admin.py` | 全新空库模式建管理员用 |
| `_opt_bidmaster_.env` | 环境变量与密钥（权限 600，另附安全提醒） |
| `restore_web_container.sh` | 重建 80 端口站点容器 |
| `expected_counts.txt` | 期望行数，导入后自动核对 |
| `containers_inspect.json` / `containers.txt` / `images.txt` | 原环境容器镜像信息 |
| `SHA256SUMS` | 完整性校验 |

传包：
```bash
scp /opt/backups/migrate_<ts>.tar.gz root@新主机:/root/
# 若打了镜像包
scp /opt/backups/api_image_<ts>.tar.gz root@新主机:/root/
```

## 3. 部署方式 A：带历史数据（推荐）

```bash
# 3.1 先把 deploy 脚本拷到新主机（包内也有一份）
#     可以直接从包里取：tar -xzf migrate_<ts>.tar.gz && 用 migrate_<ts>/backend_src.tgz 里的 deploy/
# 3.2 预演（不改动系统，只检查）
bash import_all.sh --bundle migrate_<ts>.tar.gz --dry-run
# 3.3 正式部署（含换新的数据库密码；不填则自动生成 24 位随机密码并打印）
bash import_all.sh --bundle migrate_<ts>.tar.gz --rotate-db-password
# 3.4 若老主机打过镜像包（新机不联网构建）
bash import_all.sh --bundle migrate_<ts>.tar.gz --image api_image_<ts>.tar.gz --rotate-db-password
# 3.5 若要通过域名/端口跨域访问 API，写上来源
bash import_all.sh --bundle migrate_<ts>.tar.gz --origins http://新主机IP
```

脚本会依次完成 10 步：前置检查 → 解包校验 → 放源码/compose/.env → **改 .env（换库密码等）** → 放前端与运维脚本 →
准备镜像（`docker load` 或 `docker compose build`）→ **起新的 postgres/redis** → 恢复数据卷与数据库（并逐表核对行数）→
起 api/celery → 起 80 端口站点 + 安装定时任务。

> 数据库密码为什么能在这一步换？因为 `postgres` 容器的 `POSTGRES_PASSWORD` **只在数据卷为空（首次启动）时生效**，
> 我们在启动容器之前就把 `.env` 改好了，所以新库直接就是新密码；api 的 `BMP_DATABASE_URL` 由 compose 用同一批变量拼出来，自动一致。

## 4. 部署方式 B：全新空系统

```bash
bash import_all.sh --bundle migrate_<ts>.tar.gz --fresh \
     --admin-email me@example.com --admin-password '你的强密码' \
     --rotate-db-password
# 不填 --admin-password 时脚本会生成一个 16 位随机密码并只打印一次
```

`--fresh` 模式与方式 A 的差别：
- **不**恢复数据卷、**不**灌数据库备份；
- 新库由 `db/init_pg.sql` + API 启动时的 `Base.metadata.create_all` 自动建表（**已实测**：空库 → 22 张表）；
- 第 9 步在 api 容器内执行 `seed_admin.py`：建 27 个权限、4 个角色（含 `admin`）、管理员账号并绑定 `admin` 角色（**已实测**：密码 bcrypt 校验通过）。

登录：用 `--admin-email` / 打印出来的随机密码进系统，进去后立刻改密码。

> 注意：系统**没有**自助注册接口，所以空库一定要跑这一步，否则没有账号能登录。

## 5. 新主机必须改 / 必须确认的配置（`.env` 实测清单）

| 配置项 | 当前值（老机器） | 新主机怎么办 |
|---|---|---|
| `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` | `bidmaster` / `postgres` / 24 位 | 用 `--rotate-db-password` 换新密码；库名建议保持一致（备份文件名里有库名） |
| `POSTGRES_PORT` | `127.0.0.1:5432` | 保持只绑回环；若新机已有本地 PG 占 5432，改成 `127.0.0.1:15432` |
| `REDIS_EXTERNAL_PORT` | `127.0.0.1:16379` | 同上，端口冲突就改 |
| `API_PORT` | `127.0.0.1:8000` | 保持只绑回环（外部通过 80 端口 nginx 进） |
| `WEB_PORT` | `3000` | 备用入口端口，一般不用改 |
| `ALLOWED_ORIGINS` | 空 | 同源访问（走 80 端口 nginx）可留空；要跨域直连 API 才填，用 `--origins` |
| `UVICORN_WORKERS` | `1` | **不要改**：任务与登录态在进程内存，多 worker 会"任务丢失/状态不一致" |
| `LLM_API_KEY` / `LLM_API_BASE` / `LLM_MODEL` | 有值（sensenova） | 可直接沿用；换供应商就改这三项 → 之后 `docker compose up -d --no-deps --force-recreate api celery-worker celery-beat` |
| `LLM_CHECK_MODEL` | `glm-5.2` | 同上（检查专用模型） |
| `EMBEDDING_MODE` / `EMBEDDING_API_BASE` | `api` / dashscope | `EMBEDDING_API_KEY` **当前是空的**；要用向量检索得补 key |
| `MINERU_MODE` / `MINERU_ENDPOINT` | `cloud` / mineru.net | `MINERU_API_KEY` **当前也是空的**；要用云端 OCR 得补 key |
| `BMP_DATABASE_URL` | 不在 `.env` 里 | 由 compose 用 `POSTGRES_*` 拼出并注入容器。**要指向另一台已有数据库时才需要显式设置它**（见第 9 节排错 1） |

## 6. 老机器上的"外围设施"在新机器上要重建的东西

| 设施 | 老机器现状 | 谁来做 |
|---|---|---|
| 80 端口站点容器 | `bidmaster-web`：`nginx:1.27-alpine`，**不是 compose 管理**，`docker run` 起的，端口 `80→80`、`3000→80`，挂 `dist` 与 `nginx.conf` | `import_all.sh` 调用包内 `restore_web_container.sh` 自动重建 |
| 每日 03:30 全量备份 | `backup_full.sh` + crontab | 包内有 `backup_full.sh`，导入脚本会把 2 条 crontab 装上（原 crontab 自动备份到 `/tmp/crontab.bak.*`） |
| 每 10 分钟前端看门狗 | `fe_watchdog.sh`（标记缺失即回滚 dist 到 `/opt/rollback_snapshots` 快照） | 同上自动安装；`/opt/rollback_snapshots` 会自动创建 |
| 前端守门部署 | `deploy_guarded.sh` | 同上自动安装 |
| 数据卷 | `docker_{pgdata,redisdata,projects,uploads,chroma,celerybeat}` | postgres/redis 卷由 compose 自动创建；业务卷由导入脚本恢复 |
| 网络 | `bidmaster-net`（固定名，nginx 里写死 `http://api:8000`） | compose 自动创建，**不要改名** |

## 8. 确认新主机"真的独立"（不依赖老机器）

```bash
# 8.1 .env 里不该出现老主机的 IP / 域名
grep -nE '([0-9]{1,3}\.){3}[0-9]{1,3}' /opt/bidmaster/.env || echo "  无硬编码 IP ✅"

# 8.2 数据库/Redis 指向本机容器
docker exec docker-api-1 printenv BMP_DATABASE_URL | sed 's#://[^@]*@#://***@#'   # 应为 @postgres:5432/...
docker exec docker-api-1 printenv BMP_REDIS_URL                                   # 应为 redis://redis:6379/...

# 8.3 数据卷是本机新建的
docker volume ls | grep docker_

# 8.4 唯一"共用"的是外部 AI 服务（LLM / 向量 / MinerU）——那是云 API，本来就要联网
```
> 新主机与老主机**没有任何运行时依赖**：数据库、Redis、文件、前端产物都是本地容器/本地卷，
> 只共享了云上的 LLM/向量/OCR 服务账号（如果不想共享，换一套 key 即可）。

## 9. 排错手册（都是实测踩过的坑）

1. **「我只改了 `POSTGRES_DB`，为什么还是写进了老库？」**
   容器里已经有 `BMP_DATABASE_URL`（compose 用 `POSTGRES_*` 拼好注入的），它的优先级高于单独的 `POSTGRES_DB`。
   要真正换库：改 `.env` 里的 `POSTGRES_*`，**并且**对 api 显式指定 `BMP_DATABASE_URL`，或在 compose 的 `api-env` 里让它同步变化。
   本文的导入脚本是按"整机迁移"设计的，新主机上两者天然一致，不会踩这个坑。

2. **`postgres` 起来后改密码不生效**：`POSTGRES_PASSWORD` 只在数据卷为空时生效。要么在**首次启动前**改（导入脚本就是这么做的），
   要么进容器执行 `ALTER USER postgres WITH PASSWORD '新密码';` 并同步改 `.env` 后重建 api。

3. **首页 502/一直不通**：api 首次启动要建表 + 载入模型，给它 60~90 秒；`docker logs docker-api-1` 看是否有 DB 连接错误。

4. **端口冲突**：`docker compose up` 报 `port is already allocated` → 用 `ss -ltnp | grep -E ':(80|3000|8000|5432|16379)'` 找占用者，
   或改 `.env` 里的 `API_PORT` / `POSTGRES_PORT` / `REDIS_EXTERNAL_PORT`（80/3000 由站点容器决定，改 `restore_web_container.sh`）。

5. **构建镜像失败/很慢**：优先用 `--with-image` 直接 `docker load`；否则确认能访问 `mirrors.aliyun.com`，并留出 ≥4GB 磁盘与足够内存。

6. **数据卷权限**：卷里的文件属主是容器内 `app` 用户；用 `docker run --rm -v docker_uploads:/d <镜像> tar ...` 的方式操作，不要在宿主直接改卷目录权限。

7. **前端看门狗把界面回滚了**：它只在检测到关键界面标记缺失时才回滚（快照在 `/opt/rollback_snapshots`）。
   换前端产物后应重新生成快照（`deploy_guarded.sh` 会做），否则可能被回滚回旧版。

8. **内存不足**：老机器 1.8GB 跑全套偏紧。新机器建议 4GB；`UVICORN_WORKERS=1`、`CELERY_CONCURRENCY=1` 已经是省内存配置。

## 10. 新主机上线后的日常运维

```bash
# 改代码 → 上线（构建镜像 + 重建容器 + 验证，失败自动回滚）
bash /opt/bidmaster/deploy/rebuild_and_verify.sh

# 备份：已由 crontab 每天 03:30 自动执行，产物在 /opt/backups/<日期>/
ls -la /opt/backups

# 回滚代码到上一次
docker images | grep bidmaster-pro-api            # 找 rollback-<时间戳>
docker tag bidmaster-pro-api:rollback-<ts> bidmaster-pro-api:latest
cd /opt/bidmaster/docker && docker compose up -d --no-deps api celery-worker celery-beat

# 只更新前端：把新 dist 传上去，然后用守门脚本（会先校验标记，失败自动回滚）
bash /opt/bidmaster-web/deploy_guarded.sh
```

## 11. 一句话流程

1. 老机 `export_all.sh` → 得到 26MB 的 `migrate_<ts>.tar.gz`（可加 `--with-image`）；
2. `scp` 到新机；
3. 新机 `import_all.sh --bundle migrate_<ts>.tar.gz --rotate-db-password`（要空系统就加 `--fresh --admin-email ... --admin-password ...`）；
4. 按第 7 节验证、按第 8 节确认独立性；
5. 以后用 `rebuild_and_verify.sh` 上线、`backup_full.sh`（已自动定时）备份。
